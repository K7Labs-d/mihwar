# منظومة محور التفاعلية

تصميم محور وعجلته التفاعلية، مع تنقل موحد بين أقسام الطلب والمؤجر والعرض والتنفيذ والحساب. صفحة الحساب على `/#client` متاحة من التنقل والعجلة؛ يستخدم الشخص الحساب نفسه للاستئجار والتأجير.
الصفحة تدعم إنشاء حساب بالبريد وكلمة المرور، الدخول، عرض هوية الحساب المسجل، والخروج. لا تحتوي حسابات جاهزة أو بيانات تجريبية، ولم تُعد صفحات السوق والإدارة القديمة.

## الصفحات والتنقل

المسارات التالية مبنية على الأقسام والفروع الموجودة أصلًا. تفتح مباشرة وتبقى عند تحديث الصفحة، وتدعم رجوع المتصفح وتقدمه. عناوين الصفحات والتنقل الرئيسي ووظائف الوسيط ومسار العودة تتبع المسار الحالي.

| القسم | المسار | الوظيفة الحالية |
| --- | --- | --- |
| المحور | `/` | العجلة التفاعلية وروابط الأقسام |
| الطلب | `/#request` | إنشاء طلب وحفظه في SQLite، قائمة طلبات الحساب وتفاصيلها وحالة «مفتوح» |
| تأجير معداتي | `/#broker` | التسجيل كمؤجر وإدارة المعدات والانتقال إلى وظائف الفرع |
| العرض | `/#offer` | شاشة العروض الفارغة؛ استقبال العروض ومراجعتها قيد الإكمال |
| التنفيذ | `/#execution` | شاشة التنفيذ الفارغة؛ متابعة العمل قيد الإكمال |
| العميل | `/#client` | إنشاء حساب والدخول والحساب الحالي والخروج عبر الخادم الموجود |
| إدارة الطلبات | `/#admin-requests` | صندوق طلبات العملاء والبحث والتصفية والردود للحساب المصرّح له |
| التسجيل كمؤجر | `/#broker-registration` | النموذج الحالي وحفظ طلب الاعتماد واسترجاعه من SQLite |
| معداتي | `/#equipment` | ملف المؤجر المعتمد، إضافة المعدات وتفاصيلها وتعديلها وأسعارها وتوفرها وأرشفتها |
| طلبات اعتماد المؤجرين | `/#broker-management` | الطلب الشخصي أو قائمة المراجعة حسب صلاحية الحساب |
| الفرص المشتركة | `/#broker-opportunities` | شاشة فرص التعاون الفارغة؛ الوظيفة قيد الإكمال |
| الأداء والتقارير | `/#broker-reports` | شاشة التقارير الفارغة؛ حساب الأداء وإعداد التقارير قيد الإكمال |
| الإعدادات | `/#broker-settings` | شاشة توضح عدم وجود إعدادات قابلة للتعديل بعد |

الشاشات غير المفعلة لا تنشئ بيانات أو تعرض أرقامًا مصطنعة، ولا تستدعي خدمات وهمية. روابطها تقود للأقسام الحالية المرتبطة. جدولها الفارغ يوضح شكل البيانات فقط، ولا يعني أن خدمة جلب البيانات مفعلة. في الجوال يظهر محتوى القسم قبل العجلة لتسهيل الوصول، مع الاحتفاظ بالعجلة وتصميمها. الصفحات القديمة المحذوفة لا تعود بسبب هذه المسارات.

## التشغيل

مرجع المنتج المعتمد: [Master Product Blueprint](docs/MIHWAR_MASTER_PRODUCT_BLUEPRINT.md).
حالة مرحلة المؤجر والمعدات، نموذج البيانات والترحيل والاختبارات: [Lessor Foundation + Equipment Core](docs/LESSOR_EQUIPMENT_CORE.md).

يظل `broker` في أسماء المسارات والجداول والصلاحية الحالية للتوافق؛ يمثل الآن طلب اعتماد المؤجر. عند الاعتماد ينشأ `lessor_profiles` في معاملة واحدة مع القرار. ترحيلات `schema_migrations` تنشئ ملفات للطلبات المعتمدة سابقًا مرة واحدة، وتحافظ على سجل التسجيل والحسابات. تؤخذ نسخة احتياطية متسقة من `AUTH_DB_PATH` قبل أول تشغيل للنسخة الجديدة، ولا تُرفع قواعد البيانات أو النسخ الاحتياطية إلى Git.

إدارة المعدات متاحة للمؤجر المعتمد فقط، وصلاحية `can_review_brokers` وحدها لا تمنح حق إضافة معدات. صفحة المعدات خاصة بالمالك؛ سوق المعدات العام يأتي في المرحلة التالية. الأسعار بالريال في الواجهة وبالهللة الصحيحة في SQLite، والتوفر حاليًا اختيار يدوي متاح/غير متاح، وليس تقويم حجوزات.

يتطلب Node.js 24 وnpm.

```sh
npm ci
npm run dev
```

افتح http://localhost:3000. لإيقاف الخادم اضغط Ctrl+C.

## البناء والفحص

```sh
npm run check
npm start
```

يمكن تغيير PORT وHOST باستخدام .env.local وفق .env.example. عند تغيير رابط الوصول اضبط AUTH_ORIGIN على الأصل نفسه (مثل http://localhost:3000، دون مسار).
ارفع محتويات الحزمة إلى جذر مستودع GitHub؛ لا ترفع node_modules أو ملفات البيئة الخاصة أو مجلد data أو ملفات SQLite.

## حسابات العميل

- تُحفظ الحسابات والجلسات في `data/clients.sqlite` على الخادم، وتبقى بعد إعادة تشغيله. لا تُحفظ كلمات المرور أو رموز الجلسات في localStorage.
- كلمات المرور من 12 إلى 128 حرفًا وتُخزن كتجزئة scrypt مع قيمة salt عشوائية. الجلسة عشوائية ومدتها القصوى 7 أيام ويُحفظ تجزؤ رمزها في القاعدة. الخروج يبطلها فورًا.
- ملفات الارتباط HttpOnly وSameSite=Lax، وتستخدم Secure عندما يكون AUTH_ORIGIN رابط HTTPS. HTTP مسموح للمعاينة على localhost فقط.
- توجد حدود لمحاولات الدخول وإنشاء الحساب والتحقق من مصدر طلبات المتصفح. خلف وكيل استضافة، لم يُفعّل trust proxy؛ قد يشترك المستخدمون في حد عنوان الوكيل إلى أن تضبط ذلك وفق مزودك.
- للنشر: استخدم HTTPS واضبط AUTH_ORIGIN على رابط الموقع الحقيقي، واحتفظ بمجلد data على قرص دائم مع نسخ احتياطية متسقة لـSQLite. الإعداد الحالي مخصص لعملية خادم واحدة.
- البريد معرّف للدخول ولم تُربط خدمة للتحقق من ملكيته أو استعادة كلمة المرور بالبريد بعد. لا يوجد دخول Google أو SMS أو دفع.

اختبارات الحسابات تستخدم قواعد منفصلة، وتشمل بقاء الحساب والجلسة بعد إعادة فتح القاعدة، إبطال الجلسة عند الخروج، رفض كلمات المرور الخاطئة والطلبات الخارجية، وانتهاء الجلسة وحدود المحاولات.

## طلبات العميل

طلبات العميل مرتبطة الآن بصندوق الإدارة ومحادثة داخل تفاصيل كل طلب. يستطيع صاحب الطلب قراءة ردود الإدارة والرد عليها من `/#request`، وتتابع الإدارة الطلبات من `/#admin-requests`. تشغيل اللوحة، منح الصلاحية، واجهات الربط وحدود المرحلة موضحة في [دليل استقبال الطلبات والرد عليها](docs/ADMIN_REQUEST_INBOX.md). الردود محفوظة وتُحدّث تلقائيًا أثناء فتح المحادثة؛ لا توجد رسائل بريد أو SMS.

صفحة `/#request` تستخدم الحساب والجلسة وقاعدة `AUTH_DB_PATH` نفسها. نموذج واحد بأربعة حقول: عنوان من 3 إلى 120 حرفًا، وصف من 10 إلى 2000 حرف، موقع من 2 إلى 160 حرفًا، وكمية صحيحة من 1 إلى 1000. المواعيد أو المدة المطلوبة يمكن توضيحها في الوصف حاليًا.

- جدول `client_requests`: `id` (UUID ومفتاح أساسي)، `user_id` (مفتاح أجنبي للحساب)، `title`، `description`، `location`، `quantity`، `status`، `created_at`، `updated_at`، و`submission_key` الداخلي. الحالة الوحيدة الحالية `open` وتعني «مفتوح»؛ لا توجد دورة تغيير حالة أو تعديل أو حذف في هذه المرحلة.
- `GET /api/client/requests?page=1`: طلبات صاحب الجلسة فقط، مرتبة بالأحدث، 20 طلبًا في الصفحة، مع العدد الحقيقي. `GET /api/client/requests/:id`: تفاصيل طلب مملوك للحساب؛ الطلب الغائب أو المملوك لغيره يعيد `404`.
- `POST /api/client/requests`: يقبل الحقول الأربعة فقط، ويتطلب ترويسة `Idempotency-Key` بصيغة UUID v4. الواجهة تولدها وتعيد استخدامها عند إعادة إرسال البيانات نفسها. فهرس فريد على `(user_id, submission_key)` يحسم الإرسال المتزامن: الإنشاء `201`، إعادة الطلب نفسه `200`، استعمال المفتاح مع بيانات مختلفة `409`. يمكن للحساب إنشاء عدة طلبات مستقلة.
- الملكية والحالة والتواريخ والمعرّف تأتي من الخادم. الحقول الإدارية أو غير المعروفة تُرفض بـ`400`. توجد مصادقة على القراءة والإنشاء، وقيود SQLite، ومعاملات SQL ذات بارامترات، وحماية مصدر الطلب وحد JSON الحاليان. طرق التعديل والحذف غير مدعومة وتعيد `405`.
- الواجهة لا تعلن النجاح قبل تأكيد الخادم للحفظ، ثم تسترجع التفاصيل عبر API. الطلب يبقى بعد التحديث والخروج والدخول وإعادة تشغيل الخادم. المسودة قبل الإرسال غير محفوظة ولا تستخدم localStorage.
- يمكن إضافة جدول عروض لاحقًا يحتوي `request_id REFERENCES client_requests(id)` لربط عدة عروض بطلب واحد؛ لا يوجد حقل عرض واحد أو قائمة عروض داخل الطلب. لم تُبنَ العروض أو التنفيذ أو المدفوعات أو المستندات.

اختبارات `tests/client-requests.test.mjs` تستخدم HTTP وقواعد SQLite معزولة، وتشمل الاستمرارية، الملكية، انتهاء الجلسة، التلاعب، التزامن عبر اتصالين، الصفحات، وفشل كتابة حقيقي داخل SQLite ثم إعادة المحاولة. لا تُزرع بيانات الاختبار في قاعدة المنتج.

## تسجيل الوسيط

- من فرع الوسيط اختر «تسجيل وسيط جديد» بعد الدخول بحساب العميل. بيانات الطلب تُحفظ في جدول `broker_requests` داخل قاعدة `AUTH_DB_PATH` نفسها، ويربطها الخادم بصاحب الجلسة ويضع الحالة `pending` (قيد المراجعة).
- `GET /api/client/broker-requests` يسترجع الطلب القائم أو آخر طلب لصاحب الجلسة، أو `request: null` إذا لم يوجد. `POST` على المسار نفسه ينشئ طلبًا بعد التحقق من الحقول على الخادم. لا يقبل معرف حساب أو حالة من الواجهة، ولا يُتيح قراءة طلبات مستخدمين آخرين.
- فهرس فريد في SQLite يمنع وجود أكثر من طلب قائم (`pending` أو `approved`) للحساب، حتى عند الإرسال المتزامن. الإرسال المكرر يعيد `409` مع الطلب الموجود؛ تعيد الواجهة عرضه. إذا انقطع الاتصال بعد الحفظ، يمكن إعادة المحاولة بأمان.
- الطلب وحالته يظهران في «إدارة الوسطاء» للحساب الحالي، ويبقيان بعد تحديث الصفحة أو الخروج والدخول وإعادة تشغيل الخادم. روابط `/#broker-registration` و`/#broker-management` تسترجع الحالة من الخادم عند فتحها؛ المسودة قبل الإرسال غير محفوظة. عند رفض الطلب يظهر السبب أولًا، ويمكن تقديم طلب جديد دون حذف الطلب المرفوض.
- لا توجد بنية لتخزين المستندات حاليًا: اختيار الملفات غير متاح، والطلب يُرسل دون مستندات. لا يحفظ هذا المسار ملفات أو أسماء مستندات. يلزم تخزين خاص وصلاحيات تنزيل قبل تفعيل المرفقات.
- مراجعة الطلب واعتماده أو رفضه متاحة فقط للحسابات الممنوحة صلاحية المراجعة كما هو موضح أدناه. لم يُربط تحقق خارجي من الهوية أو السجل؛ البريد المدخل في النموذج بريد تواصل، وملكية الطلب تحددها الجلسة وحدها.
- الاستضافة الفعلية تتطلب تشغيل خادم Node وقرص SQLite دائم وHTTPS، وليست استضافة ملفات ثابتة فقط. لا تنقل قاعدة المستخدمين إلى GitHub.

## مراجعة واعتماد الوسطاء

نظام الحسابات السابق لا يحتوي أدوارًا إدارية. أُضيف حقل صلاحية واحد `client_users.can_review_brokers`، وقيمته الافتراضية `0` لكل حساب جديد أو موجود. تستخدم المراجعة الحساب وكلمة المرور والجلسة نفسها، وتتحقق من الصلاحية الحالية في SQLite عند كل طلب. لا يوجد تسجيل إداري عام أو API لمنح الصلاحية، ولا تُمنح لأول مستخدم أو لبريد محدد تلقائيًا.

لمنح الصلاحية **لحساب موجود تحدده أنت**، ينفذ مشغل الخادم الأمر التالي على قاعدة `AUTH_DB_PATH` الصحيحة، باستخدام البريد الحقيقي بدل العنصر بين الأقواس:

```sh
node scripts/broker-reviewer.mjs grant <existing-account-email>
node scripts/broker-reviewer.mjs revoke <existing-account-email>
```

الأداة تقرأ `.env.local` ثم `.env` مثل الخادم، وترفض الحساب غير الموجود، ولا تنشئ حسابات أو كلمات مرور. تتطلب وصولًا محليًا إلى قاعدة الخادم. يسري سحب الصلاحية على الجلسات المفتوحة أيضًا؛ لا يوجد اعتماد على صلاحية مخزنة داخل المتصفح أو رمز قديم.

- افتح `/#broker-management` بعد الدخول. يرى صاحب الصلاحية قائمة الطلبات مع مرشحات `pending` و`approved` و`rejected` وجميع الحالات، في صفحات من 20 طلبًا. المستخدم العادي يرى طلبه فقط ولا يستطيع قراءة القائمة الإدارية أو تفاصيل طلبات الآخرين.
- `GET /api/client/broker-review/requests` للقائمة، و`GET /api/client/broker-review/requests/:id` للتفاصيل الكاملة لصاحب صلاحية المراجعة فقط.
- `POST /api/client/broker-review/requests/:id/decision` يقبل `{ "status": "approved" }` أو `{ "status": "rejected", "reason": "سبب واضح" }`. سبب الرفض مطلوب من 3 إلى 1000 حرف. الحقول الإضافية، بما فيها الملكية وهوية الإداري ووقت القرار، تُرفض.
- القرار يحدّث `status` و`decided_at` و`decided_by` و`rejection_reason` في عملية SQLite واحدة مشروطة ببقاء الحالة `pending`. لا يمكن للإداري معالجة طلبه الشخصي، ولا تغيير قرار محسوم. عند التعارض تعود `409` مع القرار المحفوظ، وعند غياب الطلب تعود `404`؛ عدم الدخول `401` وعدم الصلاحية `403`.
- يرى صاحب الطلب الحالة وتاريخ القرار وسبب الرفض. هوية الإداري محفوظة في القاعدة وتظهر في التفاصيل الإدارية فقط. الرفض لا يحذف الطلب، وإعادة التقديم تنشئ طلبًا جديدًا مع إبقاء السابق.
- الترحيل إلى أعمدة الصلاحية والقرار تلقائي عند تشغيل الخادم، ويحافظ على الحسابات والجلسات والطلبات السابقة. لا تُختلق بيانات قرار للطلبات السابقة.

اختبارات `tests/broker-review.test.mjs` تستخدم HTTP فعليًا وقواعد SQLite منفصلة على القرص، وتشمل الاعتماد والرفض وبقاء القرار بعد الخروج والدخول وإعادة فتح القاعدة، والتحقق من الصلاحيات وسحبها، ومنع المراجعة الذاتية والتعارض والتلاعب. بيانات الاختبارات لا تُضاف إلى قاعدة المنتج.
