# Lessor Foundation + Equipment Core

تاريخ مراجعة الدمج: 2026-09-24. المرجع المعتمد: [MIHWAR_MASTER_PRODUCT_BLUEPRINT.md](MIHWAR_MASTER_PRODUCT_BLUEPRINT.md).

الحالة: دُمج أساس المؤجر والمعدات من `feat/lessor-equipment-core` مع تحديثات استقبال الطلبات والمحادثات في `main`. اقتصر الدمج على المرحلة الوظيفية؛ سوق المعدات والعرض السينمائي ليسا ضمن هذا التحديث.

## الرحلة المنفذة

حساب موجود → طلب التسجيل الحالي → مراجعة بإذن `can_review_brokers` → اعتماد وملف مؤجر دائم في معاملة واحدة → `/#equipment` → إضافة معدة → SQLite → القائمة والتفاصيل → تعديل الأسعار والتوفر أو الأرشفة.

يستطيع الحساب نفسه إنشاء طلب استئجار وامتلاك معدات. الرفض أو بقاء الطلب قيد المراجعة لا ينشئ أهلية تأجير. المراجع لا يستطيع اعتماد نفسه؛ صلاحية المراجعة مستقلة عن أهلية المؤجر. أُبقيت أسماء `broker` الداخلية والمسارات القديمة؛ تغيّرت عبارات رحلة التسجيل والاعتماد إلى «المؤجر» تدريجيًا.

## النموذج والقرارات

- `lessor_profiles`: معرّف UUID، `user_id` فريد، `application_id` فريد، اسم العرض، نوع الجهة، حالة `approved`، وقت الإنشاء والتحديث. طلب التسجيل يبقى سجلًا منفصلًا يتضمن بيانات المراجعة. لا تُعاد كتابة هوية الحساب ولا صلاحياته.
- `equipment`: معرّف UUID، ملف المؤجر، اسم المعدة، تصنيف مضبوط، وصف/مواصفات، موقع نصي، سعر الساعة و/أو اليوم، العملة `SAR`، خيار المشغل، التوفر، الحالة، رقم النسخة، وقت الإنشاء والتحديث، مفتاح الإرسال وبيانات الإرسال الأصلية لمنع التكرار.
- كل سجل يمثل معدة فعلية واحدة. لا يوجد حقل كمية لمخزون مكرر. `Request.quantity` القديم لم يتغير.
- الأسعار أعداد صحيحة بالهللة، من هللة إلى 1,000,000 ريال؛ يلزم سعر واحد على الأقل. السعر نهائي لخيار `with_operator` أو `without_operator` المسجل. لا يوجد حساب عمولة أو دفع بعد.
- التوفر `available/unavailable` يدوي حاليًا؛ الحالة `active/archived` منفصلة عنه. الأرشفة لا تحذف المعدة ويمكن عكسها بالتعديل. لا توجد تقاويم حجز أو منع تعارض مواعيد في هذه المرحلة.
- لا توجد صور معدات افتراضية أو رفع صور/مستندات أو ملفات مستخدم في المستودع. الوصف النصي يتضمن المواصفات في هذه المرحلة؛ التصنيف مضبوط والموقع نصي دون إحداثيات أو Matching.

## API والضوابط

كل المسارات تحت `/api/client` وتستخدم الجلسة الحالية والتحقق من أصل طلبات POST.

| المسار | السلوك |
| --- | --- |
| `GET /lessor-profile` | ملف صاحب الجلسة أو `null` عند عدم الاعتماد |
| `GET /equipment?page=1` | معدات صاحب الجلسة فقط، 20 في الصفحة |
| `GET /equipment/:id` | تفاصيل المعدة المملوكة، وإلا 404 |
| `POST /equipment` | إنشاء بمفتاح UUID في `Idempotency-Key`؛ 201 جديد أو 200 لإعادة الإرسال نفسها |
| `POST /equipment/:id` | تعديل كامل مع `version` الحالي؛ إعادة الإرسال المطابقة للنسخة التالية مباشرة تعيد 200 دون كتابة أخرى، والمختلفة/الأقدم تعيد 409 |

الملكية والعملة والمعرّفات والتواريخ يحددها الخادم؛ تُرفض الحقول غير المعروفة. يلزم مؤجر معتمد للقراءة والإنشاء والتعديل، ولا يمكن تحديد مالك بديل. تتحقق الحدود والتعدادات والأسعار في الخادم وقيود SQLite، ولا تظهر رسالة نجاح إذا فشلت الكتابة. روابط الكيانات الجديدة تمنع حذف السجلات المرجعية.

## الترحيل والحفاظ على البيانات

تبقى تهيئة الحسابات والطلبات القديمة كما هي. الترحيلات الجديدة مرقمة ومحفوظة في `schema_migrations` تحت قفل `BEGIN IMMEDIATE`، وتُطبّق مرة واحدة أو تُلغى كاملة عند الفشل:

1. `lessor_profiles`: إنشاء الجدول وفهرس توافق ملكية الطلب، وتحويل الطلبات المعتمدة ذات الهوية الصالحة إلى ملف مؤجر واحد لكل حساب. لا تنشأ ملفات للطلبات المرفوضة أو المعلقة، ولا تُختلق بيانات قرار قديمة. وقت القرار إن وجد، وإلا وقت طلب التسجيل الأصلي.
2. `equipment_core`: جدول المعدات وقيود الأسعار والملكية والتكرار والفهرس الخاص بقائمة المالك.
3. `reconcile_approved_lessor_profiles`: إنشاء الملفات الناقصة فقط لطلبات اعتُمدت بنسخة أقدم بعد تطبيق الترحيلين 1 و2. يحافظ على الملفات السابقة وقرارات الاعتماد والجلسات وصلاحيتي مراجعة المؤجرين وإدارة الطلبات، ولا يعيد تشغيل الترحيلات السابقة.

قبل تشغيل النسخة على قاعدة موجودة، خذ نسخة SQLite متسقة في مكان محلي مستبعد من Git. لا تنسخ ملف قاعدة مفتوح منفردًا دون بيانات WAL. النسخة القديمة من التطبيق لا تعرف الكيانات الجديدة؛ احتفظ بنسخة ما قبل الترحيل للاسترداد عند الضرورة.

## التحقق

- `npm run check`: ناجح على Node.js 24.18.0، شاملًا TypeScript و47 اختبارًا وبناء Vite/الخادم وفحص تشغيل نسخة الإنتاج. بقيت اختبارات الحسابات والاعتماد والطلبات والمحادثات وإصلاح تحديث الردود ناجحة.
- الاختبارات الـ11 في `tests/lessor-equipment.test.mjs` تتحقق من الترحيل دون فقد بيانات، استقلال الصلاحيات، المعاملة الذرية للاعتماد، الملكية، القيود، منع التكرار عبر اتصالين، تعارض التعديل، فشل الحفظ، التقسيم إلى صفحات وبقاء البيانات بعد الخروج والدخول وإعادة فتح القاعدة. تشمل حالة تطبيق الترحيلين سابقًا ثم اعتماد طلب بالنسخة القديمة، والتراجع الكامل عند فشل الترحيل الثالث، وبقاء الجلسات والصلاحيات والطلبات والرسائل والمعدات السابقة.
- فحص متصفح على قاعدة مستقلة: دخول → حالة انتظار → اعتماد من مراجع آخر → دخول المؤجر → رفض نموذج فارغ → إضافة معدة وأسعار عربية عشرية → تفاصيل → تعديل توفر وأرشفة → Refresh → إعادة تشغيل الخادم باستخدام بناء الإنتاج → خروج/دخول → استرجاع المعدة نفسها والتعديلات.
- فحص سطح المكتب وعرض جوال فعلي 391 CSS px: لا تجاوز أفقي في المستند، والتنقل والنموذج والتفاصيل تعمل، ولا أخطاء JavaScript. بيانات الفحص منفصلة عن قاعدة المستخدم.
- بعد النسخ الاحتياطي، شُغّلت نسخة الإنتاج محليًا على قاعدة المشروع الأصلية. تطابقت بصمات جميع سجلات جداول الحسابات والجلسات والطلبات قبل الترحيل وبعده؛ `integrity_check=ok` ولا مخالفات للمفاتيح الأجنبية. لم تُضف معدات أو حسابات فحص إلى قاعدة المنتج.

## إصلاحات مراجعة Unicode وإعادة المحاولة — 2026-09-24

- أُعيد إنتاج المشكلات على الخادم الحقيقي بقواعد SQLite مؤقتة: فشل الترقية بسبب اعتماد قديم باسم رمز واحد، وفشل اعتماد طلب معلق مشابه، و500 في إنشاء/تعديل معدات بنص أقصر من حد SQLite، و409 عند إعادة تعديل محفوظ انقطعت استجابته.
- الحد الأدنى لاسم المؤجر ونصوص المعدات يُقاس بعد trim وNFC بعدد Unicode code points، متوافقًا مع SQLite؛ ليس بعدد UTF-16 units أو الحروف المرئية المركبة. الحدود القصوى المحافظة السابقة لم تتوسع، وتُرفض أنصاف surrogate غير المكتملة. البيانات غير الصالحة الجديدة تعيد 400 مع أخطاء الحقول قبل الكتابة.
- اعتماد طلب قديم غير صالح يعيد 422 واضحًا وتُلغى المعاملة؛ يبقى الطلب معلقًا ويمكن للمراجع رفضه مع سبب ليعيد صاحبه تقديم بيانات صحيحة. تظهر ملاحظة الهوية في تفاصيل الإدارة أيضًا.
- عند الترقية من قبل الترحيل 1 أو من الإصدار 2، لا يوقف اسم قديم غير صالح تشغيل بقية التطبيق. يُحفظ الطلب واسمه وحالة approved وقراره كما هي؛ يُؤجل إنشاء ملفه فقط، ويُكتب تحذير `LESSOR_IDENTITY_REQUIRES_CORRECTION` مع معرّفات الطلبات بعد نجاح المعاملة. أخطاء SQLite الفعلية ما زالت تؤدي إلى rollback كامل.
- صاحب اعتماد قديم متأثر يرى رسالة 409 واضحة بأن الاعتماد محفوظ ويلزم تصحيح البيانات لدى الإدارة، بدل دعوته لتسجيل جديد. لا تُتاح المعدات دون ملف صالح. **لا يوجد تصحيح تلقائي أو اسم بديل مختلق**: يصحح مشغّل مخوّل بيانات الطلب من مصدر موثوق ضمن صيانة القاعدة وبعد النسخ الاحتياطي، مع حفظ سجل الصيانة، ثم يعيد تشغيل الخادم. تعيد المطابقة عند التشغيل إنشاء الملف الناقص مرة واحدة دون تعديل القرار أو إعادة سجل الترحيلات. لم تُضف شاشة تحرير هوية أو صلاحية جديدة في هذا الإصلاح.
- تعديل المعدات وتأكيد إعادة المحاولة داخل معاملة واحدة: يعاد السجل المحفوظ فقط إذا طابقت جميع حقول الأعمال وكان `stored.version = sent.version + 1`. لا تُزاد النسخة أو التوقيت في إعادة المحاولة؛ اختلاف البيانات أو وجود نسخة أحدث يبقى 409 برسالة محايدة.
- أُضيفت 12 حالة انحدار في `lessor-unicode.test.mjs` و`equipment-unicode.test.mjs` و`equipment-retry.test.mjs`: HTTP، SQLite، قواعد قديمة مختلطة صالحة/غير صالحة، بقاء السجلات، التصحيح وإعادة التشغيل، الإنشاء والتعديل، قطع الاستجابة بعد الحفظ، الملكية والتزامن. نجح مجموع **59 اختبارًا** مع بقاء الاختبارات الـ47 السابقة.
