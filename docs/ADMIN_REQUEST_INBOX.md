# استقبال الطلبات والرد عليها

هذه المرحلة تربط طلب العميل المحفوظ بلوحة تشغيل للإدارة ومحادثة داخل الطلب نفسه. تعتمد على الحسابات والجلسات وSQLite الموجودة. يمكن مراجعتها ودمجها على `main` بصورة مستقلة عن مرحلتي المؤجر والمعدات والسوق المفتوحتين.

## معيار القبول والرحلة

1. العميل يسجّل الدخول ويفتح `/#request` وينشئ طلبًا.
2. المشغّل يمنح حساب إدارة موجودًا صلاحية استقبال الطلبات محليًا على الخادم.
3. حساب الإدارة يفتح `/#admin-requests`: يرى الطلب واسم العميل وبريد حسابه والموقع والكمية والوصف والتاريخ.
4. الإدارة تفتح الطلب وتكتب ردًا. النجاح يظهر بعد تأكيد الحفظ في الخادم فقط.
5. العميل يفتح تفاصيل الطلب ويقرأ الرد ويرسل توضيحًا عند الحاجة.
6. يعود الطلب إلى مرشح «بانتظار رد الإدارة» إذا كان آخر رد من العميل. الطلب الذي لم تبدأ محادثته ينتظر الإدارة أيضًا.
7. الطلبات والرسائل تبقى بعد الخروج والدخول وإعادة تشغيل الخادم.

صندوق الإدارة يدعم البحث في العنوان والموقع ومعرّف الطلب واسم العميل وبريده، والتصفية والصفحات (20 طلبًا في الصفحة). العدادات حقيقية، وتشير إلى آخر طرف ردّ؛ «تم رد الإدارة» لا تعني أن العميل قرأ الرد أو وافق على حجز. الصندوق والمحادثة يتحدثان كل 15 ثانية أثناء فتح الصفحة، وعند عودة التركيز إليها. الردود داخل التطبيق فقط.

## التشغيل ومنح الصلاحية

استخدم Node.js 24. شغّل `npm ci` ثم `npm run check` ثم `npm start` بعد إعداد `.env.local` بحسب `.env.example`. احتفظ بقاعدة `AUTH_DB_PATH` على قرص دائم وخذ نسخة SQLite متسقة قبل ترقية النسخة. النشر العام يحتاج HTTPS و`AUTH_ORIGIN` مطابقًا للأصل الحقيقي.

أنشئ حسابك من واجهة الحساب أولًا، ثم نفّذ في مجلد المشروع على الخادم، مع استبدال البريد ببريد الحساب الموجود:

```sh
node scripts/request-manager.mjs grant existing-account@example.com
```

افتح الحساب أو حدّثه لتظهر وصلة «إدارة الطلبات»، أو افتح `/#admin-requests` مباشرة. لإلغاء الصلاحية:

```sh
node scripts/request-manager.mjs revoke existing-account@example.com
```

الأداة تستخدم `.env.local` ثم `.env` وقاعدة `AUTH_DB_PATH` نفسها. لا تنشئ حسابات، ولا كلمات مرور، وترفض بريدًا غير موجود. لا يُمنح أول حساب صلاحيات تلقائيًا. لم يُجهّز حساب إنتاج أو تُمنح صلاحية لحساب المستخدم ضمن الاختبارات. صلاحية `can_manage_requests` منفصلة عن `can_review_brokers`؛ حساب مراجعة المؤجرين لا يحصل تلقائيًا على طلبات العملاء.

## البيانات وواجهات الربط

يُضاف عمود `client_users.can_manage_requests` افتراضيًا بقيمة صفر، وجدول `request_messages` مرتبط بـ`client_requests` وصاحب الرد. يحفظ الجدول ترتيب الرسائل ومعرّفها ونصها ووقت إنشائها والطرف المرسل ومفتاح منع التكرار. تبقى بيانات الطلب وحالته التجارية `open` دون تغيير. لا تُعرض هوية الموظف أو بريدُه للعميل؛ يظهر الرد باسم «إدارة محور»، مع حفظ هوية المرسل داخليًا.

جميع المسارات تحت `/api/client`:

| المسار | الوصول والنتيجة |
| --- | --- |
| `GET /request-inbox?page=1&filter=all&q=` | الإدارة فقط؛ قائمة وصفحات وعدادات. المرشحات: `all` و`unanswered` و`answered`. |
| `GET /request-inbox/:id` | الإدارة فقط؛ الطلب واسم العميل وبريد الحساب. |
| `GET/POST /request-inbox/:id/messages` | الإدارة فقط؛ قراءة المحادثة أو إضافة رد إداري. |
| `GET/POST /request-conversations/:id/messages` | صاحب الطلب فقط؛ قراءة المحادثة أو إضافة رد العميل. |

قراءة الرسائل تعيد آخر 50 رسالة بترتيب زمني تصاعدي و`hasMore`. استخدم `before=<sequence>` للرسائل الأقدم أو `after=<sequence>` للتحديث التزايدي؛ لا تجمعهما. الإنشاء يقبل `{ "body": "نص الرد" }` وترويسة `Idempotency-Key` بصيغة UUID v4. النص بين حرف و2000 حرف. يحدد الخادم الطرف والمالك والتاريخ.

الحفظ الأول يعيد `201`؛ إعادة الطلب نفسه تعيد `200` مع الرسالة نفسها، واستخدام المفتاح لنص أو دور مختلف يعيد `409`. حدّ الإرسال 20 رسالة في الدقيقة للحساب عبر جميع طلباته، محفوظ في قاعدة البيانات. استرجاع نتيجة رد محفوظ مسموح حتى عند بلوغ الحد. الرسائل نص عادي، ولا تقبل HTML قابلًا للتنفيذ أو مرفقات. تعديل الرسائل وحذفها غير متاحين.

يُتحقق من الجلسة والصلاحية الحالية في كل قراءة وإرسال. سحب الصلاحية يسري على الجلسات المفتوحة؛ تمسح الواجهة بيانات الطلب عند تلقي رفض الوصول. لا يمكن للعميل قراءة أو مراسلة طلب غيره حتى لو عرف معرّفه. حماية مصدر الطلب وHttpOnly والتحقق من الحمولة وحد حجم JSON الموجود يطبّق على هذه المسارات أيضًا.

## التحقق والحدود

`tests/request-inbox.test.mjs` يغطي دورة العميل والإدارة كاملة عبر HTTP وSQLite معزولة، الاستمرار بعد إعادة التشغيل، الصلاحيات وسحبها وانتهاء الجلسات، خصوصية الطلبات، رفض التلاعب والطلبات الخارجية، التزامن وإعادة المحاولة، فشل كتابة فعلي، البحث والصفحات ومؤشرات الرسائل وحد الإرسال. تُفحص مسارات الربط أيضًا عند تشغيل بناء الإنتاج. بيانات الاختبارات لا تُضاف إلى قاعدة المنتج.

نتيجة التحقق في هذه المرحلة: نجح `npm run check`، شاملًا TypeScript وجميع الاختبارات الـ34 وبناء الواجهة والخادم وفحص تشغيل الإنتاج. لم تُضف تبعيات جديدة.

هذه مرحلة استقبال ومراسلة. لا تنشئ عرض تأجير أو حجزًا أو دفعة، ولا تمنح اعتماد مؤجر أو تغيّر الحالة التجارية للطلب. تعيين موظف، الإغلاق التجاري، المرفقات، والتنبيهات بالبريد أو الهاتف ليست ضمن هذه المرحلة. تُربط الكيانات اللاحقة بمعرّف الطلب نفسه عند تنفيذها وفق خريطة المنتج.

فحص المتصفح المرئي في جلسة التنفيذ تعذر بسبب عدم قدرة المتصفح المتاح على فتح الخادم المحلي. لا تُعد اختبارات HTTP أو نجاح البناء إثباتًا لفحص بصري مكتمل على الجوال؛ يلزم فحص الواجهة على بيئة المعاينة قبل النشر العام.
